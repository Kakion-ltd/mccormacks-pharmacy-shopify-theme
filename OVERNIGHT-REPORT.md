# Phase A — findings

## 1. Canonicals — mostly unanswerable locally

**The theme emits one unmodified `{{ canonical_url }}`** and nothing else. No
`rel="next"`/`rel="prev"`, no `noindex`, no hreflang, no robots directives, and no
custom canonical logic anywhere. So on all five URL shapes you asked about, the
answer is whatever Shopify puts in that variable.

I could not observe that. The preview harness hardcodes `canonical_url` to a fixed
string, and Shopify's documentation for it does not state whether query parameters,
filters or search strings are included. **Rather than assert five canonical values
from memory, I stopped** — see Q1. The verification procedure is at the end of this
section; it is about ten minutes on the dev store.

What I *could* establish is where duplicate paths come from, since that is the
theme's own doing:

| Path shape | Generated by | Crawlable? |
|---|---|---|
| `/collections/x/products/y` | `main-collection.liquid`, 4 links per product card | **Yes — was linked from all 293 collection pages.** Fixed, see Phase C |
| `?page=N` | `{% paginate %}` at `main-collection.liquid:160`, standard Shopify pagination links | Yes |
| `?sort_by=` | the sort `<select>` — JS sets the param and navigates | **No.** A `<select>` is not a link, so no crawlable URL is created |
| `?filter.*` | Shopify's native `collection.filters` | Yes, when filters are configured |
| `/search?q=` | the header form | Linked from nowhere; reachable only by submitting |
| `/collections/x/<tag>` | **nothing** — the theme emits no tag links at all | n/a |

Two useful observations from that table. The sort control creates no crawlable
duplicates, which is the good outcome and worth not breaking. And the theme never
generates tag-filtered URLs, so that row of your brief has no theme-side exposure —
though tag URLs can still be reached if anything else links to them.

### Canonical verification procedure — for the dev store

Load each URL and read `<link rel="canonical">` from view-source:

1. `/collections/vitamins/products/<any-product>` — expect `/products/<handle>`
2. `/collections/vitamins?page=2` — does the canonical keep `?page=2` (self-referencing,
   correct) or drop to page 1 (which would de-index pages 2+)
3. `/collections/vitamins?filter.v.price.gte=10` — does it drop the filter
4. `/collections/vitamins/some-tag` — does it drop the tag
5. `/search?q=nurofen` — expect `/search` with no query

Items 2, 3 and 4 are the ones that could require theme-level work. Item 2 in
particular is worth checking carefully: a canonical that points every paginated page
back to page 1 hides deep products from Google entirely, which matters on a
293-collection catalogue.

## 2. Internal linking — genuinely good, with one caveat

Measured by building a link graph over the 344 rendered pages and running a
breadth-first walk from the homepage.

- **Orphans: none.** 293 of 293 collections have at least one inbound internal link.
  (The graph reported one "orphan" called `index`, which is an artefact of my file
  glob picking up `preview/categories/index.html`, not a real collection.)
- **Click depth: 2, maximum.** 216 collections are one click from the homepage, the
  remaining 77 are two. There is no deep tail.

That result comes almost entirely from the mega-menu, which carries 207
destinations on every page. Worth stating plainly: **sitewide navigation links are
weaker signals than contextual ones.** Everything is reachable, but nearly all of it
is reachable the same way, so the internal link graph tells Google very little about
which collections matter more than others. That is a content-strategy question
rather than a bug, and I have not acted on it.

### Related-product rails

- **PDP rail** (`main-product.liquid:16-21`) uses `recommendations.products`, which
  Shopify generates per product, so links vary. It falls back to
  `collections[product.collections.first.handle].products` when recommendations have
  not been performed — and **that fallback does repeat**: every product in a given
  collection shows the same set. How often it fires depends on how quickly Shopify's
  recommendation engine warms up on a new store, which cannot be measured here.
- **Cart cross-sell** (`cart-recommendations.liquid:25`) uses
  `recommendations.products` with no repeating fallback.
- **`sale-products` and `popular-categories`** are fixed rails driven by a chosen
  collection, so they *do* link the same products sitewide — but that is what they
  are for, and they are single sections rather than per-product rails.

## 4. Alt text — 4,884 empty of 6,678

Across 344 rendered pages:

| Type | Total | `alt=""` before |
|---|---|---|
| Product images | 4,917 | **4,884** |
| Logos | 1,370 | 0 |
| PSI mark | 344 | 0 |
| Category / brand / slides / everything else | 47 | 0 |

**No image was missing the attribute** — the problem was that `image_tag` was being
called with no `alt:` argument in five places, so Shopify fell back to the image's
admin alt field, which is blank for a bulk-imported catalogue. The PDP gallery and
its thumbnails passed `media.alt`, blank for the same reason.

The practical effect: a screen reader announced a collection grid as a list of
prices with no products attached.

# Phase B — built

## 5. Dynamic alt text — `snippets/image-alt.liquid`

One snippet, four rules, first match wins:

1. **Whatever a person typed in the admin.** Manual alt text always survives — the
   fallback only ever fills a gap. Putting this first is the whole reason the rule
   lives in one snippet rather than at each call site.
2. **Product title**, plus the variant name when the image belongs to a specific
   variant (`image.attached_to_variant?`). "Sudocrem — 250g" rather than the same
   title five times.
3. **Collection title**, for category imagery.
4. **Empty**, for decoration.

Wired into all six product/collection image call sites.

**Two images left deliberately empty.** In predictive search the thumbnail sits
inside the same `<a>` as the product title; in the cart cross-sell the thumb link is
`aria-hidden="true"` with the title in its own link alongside. An empty alt is
correct in both, and repeating the title would make a screen reader say it twice.
Verified they are still empty after the change.

**Result: 6,678 images, 0 empty, 0 missing**, decorative cases preserved.

What this does not do is describe what is *in* each picture. That needs a human who
can see it, and per your hard limits I have written no descriptive copy.

## 6. Product FAQ — `snippets/product-faq.liquid`

Mechanism only. **Populated with nothing.**

Reads a `custom.faq` JSON metafield, renders a native `<details>` accordion on the
product page, and emits `FAQPage` JSON-LD from the same data through the same
validation, so the visible copy and the schema cannot drift apart.

- **Fails closed three ways.** Absent or non-list metafield → nothing rendered, no
  schema. An entry missing either half → dropped entirely, not rendered as a question
  with no answer. Nothing left → the section is omitted, not left as an empty heading.
- **Internal links in answers work.** Answers may contain HTML; the visible copy
  renders it, the JSON-LD carries it json-encoded so punctuation cannot invalidate
  the block.
- **`<details>` rather than a JS accordion** — keyboard-operable with no script, and
  the answers stay in the DOM when collapsed, which is what makes them eligible for
  the rich result.

The metafield *definition* has to be created in the admin and I could not do that;
steps are in `setup/MAINTENANCE.md` and in Q3.

**On populating it:** FAQPage markup makes answers eligible to appear directly in
Google's results, detached from the page and any surrounding context. On medicine
products that is a higher bar than ordinary product copy, which is why the mechanism
ships empty.

# Phase C — fixed

## 7. Collection grids now link to the canonical product URL

`main-collection.liquid` used `product.url | within: collection` in 4 places,
producing `/collections/<handle>/products/<handle>`. Every other surface used the
plain `/products/<handle>` — 14 plain links against 4 scoped ones.

Treated as unambiguous because **the plain URL is the better target under both
possible answers to Q1**: if Shopify canonicalises the scoped URL, those links were
spending internal link equity on a URL that only points elsewhere; if it does not,
the theme was minting a duplicate URL for every product on 293 pages.

The usual reason to keep `within:` — giving the PDP a `collection` object for
back-to-collection links or collection-aware breadcrumbs — does not apply: this
theme never reads it. The PDP breadcrumb is built from `product.collections.first`.

Rendered output now contains **0** collection-scoped product URLs. One commit to
revert (`bf642fa`) if you disagree.

**Left alone as ambiguous:** everything in Q1. No canonical logic was added, because
adding it without knowing what Shopify already does risks double-canonicalising.

# Follow-up — 27 August, after review

## ItemList and SearchAction

Both built; commit `d3e69a5`. Sitewide JSON-LD now: **959/959 blocks parse**, with
306 `ItemList`, 306 `BreadcrumbList`, 342 `Pharmacy`, 1 `WebSite`.

`ItemList` covers only the paginated slice, not the whole collection — claiming 400
products on a page showing 24 is a mismatch between markup and content. Each entry
is position + url + name, not a nested `Product`: the product page already carries
the full `Product` node, and a partial second copy gives Google two sources for the
same facts. It stays silent on an empty collection.

`SearchAction` is homepage-only and builds its target from `routes.search_url`, so a
locale or market prefix survives. Its `publisher` points at the `#organization` node
the footer already emits, so the graph joins up rather than floating free. It is a
request rather than a guarantee — the sitelinks search box appears only where Google
already shows sitelinks for the brand.

The empty-collection branch renders in no preview, since every mock collection holds
the same 10 products, so both are unit-tested at snippet level: 13 checks covering
the empty guard, absolute URLs, position ordering, a quoted product title, and a
locale-prefixed search route. `npm test` is now 45 checks.

Writing those surfaced a robustness gap worth noting: `{{ shop.name | json }}` with
no value emits *nothing* rather than `null`, which invalidates the entire block.
Shopify always sets a shop name so this could not fire on a live store, but liquidjs
and Shopify differ here and the preview would have shipped invalid JSON-LD. Guarded.

## Breadcrumbs after the `within:` change — verified, not assumed

**Result: identical on every entry path.** Checked by loading the same product three
ways and reading the rendered breadcrumb:

| Entry path | Breadcrumb |
|---|---|
| `/products/fabu-…` | Home / Skin, Hair & Nails / fabÜ Skin Hair Nails Glow 60 Capsules |
| `/collections/skin-hair-nails/products/fabu-…` | *identical* |
| `/collections/vitamins/products/fabu-…` | *identical* |

The reason it is identical is the thing worth knowing: **the breadcrumb is built from
`product.collections.first`, not from the URL.** It never read the `collection` object
that `within:` populates, so the change could not have affected it — and the third row
shows the consequence. A visitor arriving from Vitamins still sees "Skin, Hair &
Nails", because that is the product's first collection.

That behaviour is unchanged by this work and I have not touched it, but it is a real
limitation: the breadcrumb reflects Shopify's collection ordering rather than the path
the visitor took. Restoring path-awareness would mean reading the `collection` object
and therefore restoring `within:` — the opposite of the canonical fix. The two goals
are in direct tension, and which wins is a judgement call rather than a bug fix.

### Two more harness blind spots, both fixed

Verifying this could not be done at first, for two reasons that are the same class of
problem as the missing sold-out fixture — a real path that rendered nowhere:

1. **`product.collections` was `[]` on every mock product**, so the breadcrumb's middle
   segment had never rendered in any preview.
2. **`serve_preview` routed `/collections/<c>/products/<p>` to the collection page**,
   because the `/collections/` branch matched first. Shopify serves that path as the
   product page, so the entire collection-scoped product URL was untestable — the exact
   path the `within:` change was about.

Both fixed in `9c2c00b`. The pattern is now familiar enough to state plainly: when a
code path renders in no preview, it gets verified by nobody, and it ships on
assumption.
